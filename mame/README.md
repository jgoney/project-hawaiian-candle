# RR206 MAME debugger workflow

MAME 0.288 identifies the system as `genesis`, the cartridge slot as `cart`,
and the Motorola MC68000 as `:maincpu`. All MAME-generated state is redirected
to the ignored `generated/mame/` directory.

Start with the interactive bike-load breakpoint:

```sh
./scripts/run-mame-debug-rr206.sh
```

The command file starts execution automatically. The debugger stops at `0xDD24`,
immediately after the selected player's 38-byte tuning record has been copied to
`0xFF0546`. Use `g` in the debugger console to continue. The backtick/tilde key
breaks back into the debugger during play.

For a sampled player-physics log:

```sh
./scripts/run-mame-debug-rr206.sh \
  "Road Rash II (USA, Europe) (RR206).gen" \
  mame/rr206-physics-log.cmd
```

That command samples the `0x1A948` motion-delta write path approximately once
per 60 player-vehicle updates and prints:

- candidate speed at player object `+0x12` (`0xFF0A74`);
- computed signed delta from `D1`, about to be stored at `+0x14`;
- candidate gear at `+0x18` (`0xFF0A7A`);
- selected raw controller byte, throttle counter, and nitro parameter.

The logger is intentionally observational: it reads emulated RAM but does not
patch either RAM or ROM.

MAME writes each run to `generated/mame/error.log`, replacing the previous
run's log. Physics samples begin with `RR2TRACE` and use this CSV-compatible
field order:

```text
RR2TRACE,sample,speed,delta,gear,input,throttle,nitro
```

Play the desired test, exit MAME normally, and preserve the trace before the
next run. For example:

```sh
cp generated/mame/error.log generated/mame/full-throttle.log
```

## Complete work-RAM capture

For a complete 64 KiB work-RAM image at every emulated frame, stored as an
initial snapshot plus changed bytes, run:

```sh
./scripts/run-mame-ram-capture-rr206.sh \
  "Road Rash II (USA, Europe) (RR206).gen" \
  full-throttle
```

This also creates a MAME `.inp` recording. See `analysis/ram-capture.md` for the
format, validation command, and interpretation limits.

## Deterministic physics replay

Replay a recorded input stream at unrestricted speed while logging every final
player motion-delta store at `0x1A948`:

```sh
./scripts/replay-mame-physics-rr206.sh \
  "Road Rash II (USA, Europe) (RR206).gen" \
  full-throttle
```

Rows beginning with `RR2PHYS` are written to `generated/mame/error.log`. They
include speed, signed delta bits, gear, vehicle flags, slope input, raw control
input, throttle state, and nitro state.

An optional third argument replaces the debugger command file. To log every
game-loop timestep handoff at `0xDF48` instead:

```sh
./scripts/replay-mame-physics-rr206.sh \
  "Road Rash II (USA, Europe) (RR206).gen" \
  full-throttle \
  mame/rr206-timestep-replay.cmd
```

Rows beginning with `RR2TICK` give the loop pass, cumulative VBlank count,
cumulative accumulator increments, timestep (`D1`; use its low word), and the
`0xFF254E` flag.

## Reference trace windows for the native port

The port's translated code is checked against instruction-level traces of the
original. Record a window with:

```sh
./scripts/run-mame-port-trace-rr206.sh boot
./scripts/run-mame-port-trace-rr206.sh race
./scripts/run-mame-port-trace-rr206.sh race-start
./scripts/run-mame-port-trace-rr206.sh race-early
```

- `boot` runs from just after reset (`0x206`; the debugger script cannot see
  the first instruction) to the 30th VBlank after the front end is entered at
  `0xCBCC8`.
- `race` replays `generated/mame/full-throttle.inp` and covers game-loop
  handoffs 500 to 520 at `0xDF48`.
- `race-start` and `race-early` replay the same recording and cover handoffs
  2 to 14 and 14 to 44: the start of the race, where the native port's timing
  first parted from MAME's.

Each window is written to the ignored `generated/port/traces/<window>/`:

| File | Contents |
| --- | --- |
| `trace.txt` | One line per instruction about to execute: `T pc sr d0-d7 a0-a7 totalcycles`. The last such line's instruction is not executed. The file ends with `E <count>`; a file without it is truncated and is rejected. |
| `hw.txt` | Every 68000 access to `0x100000-0xDFFFFF` in order: `R\|W addr size value`. |
| `ram-start.bin`, `ram-end.bin` | Work RAM at the first and last trace line. |
| `handoff-NN.bin` | Work RAM each time `0xDF48` is about to execute (race only). |
| `meta.txt` | ROM hash, MAME version, window name, input recording. |

The debugger script is generated by `rr2port.mame_cmd`. Three MAME behaviours
shape it (all verified on 0.289):

- bare numbers in debugger expressions are hexadecimal, so counts are written
  with a `0x` prefix;
- the `pc` symbol is one word past the instruction start, so the PC is taken
  from the disassembly line that `trace` writes after each register line;
- `trace` logs an instruction before breakpoints at that address run, so a
  trace started inside a breakpoint action begins with the next instruction.

The run needs `-debugger osx`; with `-debugger none` the script is ignored.
A window takes several minutes and a few gigabytes of temporary disk space.

## Recording indirect jump targets

The translator finds code from `port/annotations/rr206.toml`. To check or
extend the annotations for indirect jumps and calls, replay a recording with a
breakpoint on every indirect site and log where each one goes:

```sh
for c in full-throttle wild-thing-controls controller-test; do
  ./scripts/run-mame-indirect-log-rr206.sh $c
done
uv run rr2-annotate-indirect port/annotations/rr206.toml \
  generated/port/indirect/*.txt --rom "Road Rash II (USA, Europe) (RR206).gen"
uv run rr2-code-report "Road Rash II (USA, Europe) (RR206).gen" \
  --annotations port/annotations/rr206.toml \
  --window generated/port/traces/boot --window generated/port/traces/race
```

Each run writes the distinct `site target` pairs to
`generated/port/indirect/<capture>.txt`. `rr2-annotate-indirect` merges them
into the `[jump_tables]` section, which must stay the last section of the
file, and rejects any target that is odd, outside the ROM or not decodable.
New targets can expose new code and so new indirect sites; repeat until a
round adds nothing. A recording takes one to three minutes.

## Reference pictures of the boot sequence

```sh
./scripts/run-mame-boot-pictures-rr206.sh
```

writes `generated/port/pictures/boot-vNNNN.png`, MAME's 320x224 snapshot at the
NNNNth entry to the VBlank handler (`0x11B8`) since power-on, by default every
60 entries up to 1200. Counting handler entries, not frames, lets the port stop
at the same point without sharing MAME's frame numbering. With no input the
sequence is: Electronic Arts logo (around entry 240), a black frame (420),
then the title screen with rotating credits (480 onwards).

Two MAME 0.289 behaviours shape the script (both verified):

- a debugger `snap` followed by `quit` leaves MAME hung on exit, so the script
  runs MAME in the background and stops it once the last picture exists;
- taking a snapshot while a `trace` is active hangs the same way, which is why
  trace windows take no picture.

The boot trace window ends while the screen is still black, so it is no use as
a picture reference.

## Beam position at counter reads

```sh
./scripts/run-mame-hv-log-rr206.sh
```

replays `full-throttle` and, over the same handoffs as the race trace window,
writes `generated/port/hv/race.txt`: `RR2HV <addr> <bits> <value> <beamx>
<beamy> <totalcycles>` for each read of the HV counter port and `RR2INT
<level> <beamx> <beamy> <totalcycles>` as each interrupt handler is entered.
`rr2port.hv` reads and fits it; `analysis/video-timing.md` has the results.
MAME's `beamy` is not the hardware line number: hardware line = (beamy + 38)
mod 262, and the V counter steps at beam column 462, not 0.

## MAME's video memory at a VBlank entry

```sh
./scripts/run-mame-vdp-state-rr206.sh 660
make -C port vdp-render
generated/port/build/rr-vdp-render --state generated/port/pictures/state-v0660.bin \
  -o generated/port/pictures/state-v0660.ppm
```

The script stops MAME's debugger at the Nth entry to the VBlank handler and
`mame/rr206-vdp-state.lua` then writes the video chip's registers, VRAM, CRAM
and VSRAM (`state-vNNNN.bin`) and work RAM (`state-vNNNN-ram.bin`).
`rr-vdp-render` draws the state with the port's renderer.

This is the picture reference to trust. MAME's own snapshot at the same entry
shows the frame before (verified: `analysis/video-timing.md`). Counting
entries from Lua with a read tap on the handler address does not work (the
address is read more than once per entry, and not consistently), which is why
the debugger does the counting.

## Work RAM at every game-loop handoff

```sh
./scripts/run-mame-handoff-capture-rr206.sh full-throttle
```

replays a recording with the debugger stopping at every execution of
`0xDF48`; `mame/rr206-handoff-ram.lua` saves work RAM at each stop and
resumes. Output: `generated/port/handoffs/<capture>.bin` (changes from one
handoff to the next; format in `src/rr2port/handoffs.py`) and
`<capture>.timesteps` (the timestep about to be stored at each handoff),
`<capture>.pads` (every controller read in order, `1 XX` or `2 XX` for the
port and the byte the game's read routine returned, with an `H` line at each
handoff so a replay can line reads up pass by pass) and `<capture>.regs` (per
handoff: MAME's cycle count, the status register, D0-D7 and A0-A7). The
script fails unless the number of handoffs equals the number of `RR2TICK` rows
in the capture's timestep log. `rr-race-replay` compares a native race with
it; see `analysis/race-conformance.md`.
